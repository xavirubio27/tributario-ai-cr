## 1. Hechos verificados de Resend / Svix (fundamentan el diseño)

| Hecho | Valor | Fuente |
|---|---|---|
| Timeout del endpoint de webhook | **15 s** para responder 2xx | Svix (Resend usa Svix) `[VERIFICADO]` |
| Programación de reintentos | inmediato · 5 s · 5 min · 30 min · 2 h · 5 h · 10 h · 10 h | Resend/Svix `[VERIFICADO]` |
| Ventana total de reintento | hasta ~24 h; **replay manual** de mensajes `failed` y `succeeded` | Resend `[VERIFICADO]` |
| Entrega | **at-least-once**; dedup por `svix-id` | Resend `[VERIFICADO]` |
| Endpoint que falla de forma sostenida | Resend **lo deshabilita automáticamente** y notifica por correo | Resend `[VERIFICADO]` |
| Recomendación oficial | "recibir y **encolar** para procesar async; responder pronto" | Svix `[VERIFICADO]` |
| Contenido del webhook `email.received` | **NO** incluye cuerpo/cabeceras/adjuntos; solo metadata | Resend `[VERIFICADO]` |
| Recuperación del RAW | endpoint *Retrieve Received Email* → objeto `raw` con `download_url` (CloudFront firmada) + `expires_at` | Resend `[VERIFICADO]` |
| Validez del `download_url` | **1 hora**; re-solicitable llamando de nuevo a la API | Resend `[VERIFICADO]` |
| Contenido del RAW | `.eml` original completo, **incluye todos los adjuntos** (base64 inline) | Resend `[VERIFICADO]` |
| Límite de tamaño de **envío** | 40 MB (incluidos adjuntos tras base64) | Resend `[VERIFICADO]` |
| Límite de tamaño **inbound** | **sin ceiling contractual localizado** | `[VERIFICADO]` (ausencia) |
| Retención del email recibido para re-fetch | ≥17 días | C4-B0 `[OBSERVADO]` |

**Consecuencia rectora:** el RAW **no viaja en el webhook**; hay que hacer un fetch de 2
pasos (API → CloudFront) de hasta **64 MiB** (política Tribuu, §5). Hacer ese fetch de forma
**totalmente síncrona dentro del presupuesto de 15 s** es frágil para la cola de tamaños
grande y contradice la guía oficial de Svix. Esto obliga a la arquitectura de **captura en
dos fases** (§4.1), que es el cambio central de A3 respecto de A2.

## 2. Resolución de las decisiones abiertas D1–D7

| # | Decisión | Resolución `[PROPUESTO]` salvo indicación |
|---|---|---|
| **D1** | Sede/documentación del diseño físico | **Resuelta por el orquestador:** vive en **este** `docs/design/C4-B3.md`; ADR-050 permanece DRAFT y absorberá las decisiones al aceptarse. |
| **D2** | ACK ante `evidence_conflict` | Disposición **terminal** + alerta fuerte, **tras** preservar durablemente los bytes conflictivos como blob nuevo (`terminal != descartar evidencia`). La redacción "RAW / adjuntos / ACK" del árbol de PROJECT_STATE debe aclararse: en B3 los adjuntos se **preservan dentro** del blob RAW, no como blobs separados. |

## 3. C4-B3-A2 consolidado — modelo físico (schema `inbound`, backend-only)

> Pseudo-DDL **ilustrativo** del diseño, no una migración. Cambios respecto de la propuesta
> A2 previa marcados como **[Δ A3]**.

### 3.1 `inbound.evidence_blobs`
```
id               uuid        PK  DEFAULT gen_random_uuid()
company_id       uuid        NOT NULL
sha256           bytea       NOT NULL                       -- 32 bytes, identidad canónica
size_bytes       bigint      NOT NULL
storage_backend  text        NOT NULL DEFAULT 'postgres_bytea'
bytes            bytea       NULL
object_locator   text        NULL
content_type     text        NOT NULL DEFAULT 'message/rfc822'
source_kind      text        NOT NULL                        -- p.ej. 'inbound_email_raw'
created_at       timestamptz NOT NULL DEFAULT now()

PK      (id) · UNIQUE (company_id, id)
CHECK   storage_backend IN ('postgres_bytea','object_storage')
CHECK   octet_length(sha256) = 32
CHECK   size_bytes >= 0                                      -- SIN tope MAX en el esquema (§5)
CHECK   bytes IS NULL OR octet_length(bytes) = size_bytes
CHECK   bytes IS NULL OR extensions.digest(bytes,'sha256') = sha256   -- ver R6
CHECK   storage_backend <> 'postgres_bytea' OR bytes IS NOT NULL
CHECK   bytes IS NOT NULL OR object_locator IS NOT NULL      -- nunca sin copia
CHECK   storage_backend <> 'object_storage'  OR object_locator IS NOT NULL
```

### 3.2 `inbound.provider_events`  **[Δ A3: estado de intake + columnas de reintento]**
```
id                  uuid        PK  DEFAULT gen_random_uuid()
company_id          uuid        NOT NULL        -- solo recipients ACTIVE_RESOLVED
inbox_id            uuid        NOT NULL
provider            text        NOT NULL
provider_event_id   text        NOT NULL        -- svix-id
provider_email_id   text        NULL            -- data.email_id
event_type          text        NOT NULL        -- 'email.received'
provider_timestamp  timestamptz NULL
email_message_id    uuid        NULL            -- set en captured/linked/conflict (fase 2)
observed_blob_id    uuid        NULL            -- blob observado por ESTE evento (fase 2)
state               text        NOT NULL        -- [Δ A3] ciclo de intake (abajo)
raw_webhook         bytea       NOT NULL        -- bytes verificados por Svix (fase 1)
webhook_sha256      bytea       NOT NULL        -- 32 bytes
webhook_size_bytes  bigint      NOT NULL
attempts            int         NOT NULL DEFAULT 0   -- [Δ A3] intentos de fase 2
next_attempt_at     timestamptz NULL                 -- [Δ A3] backoff
last_error          text        NULL                 -- [Δ A3] diagnóstico sin PII
captured_at         timestamptz NULL                 -- fijado al llegar a estado terminal exitoso
created_at          timestamptz NOT NULL DEFAULT now()

PK      (id) · UNIQUE (company_id, id)
UNIQUE  (provider, provider_event_id, inbox_id)      -- idempotencia de EVENTO
CHECK   provider = 'resend'
CHECK   event_type = 'email.received'
CHECK   state IN ('received','captured','linked_existing',
                   'evidence_conflict','rejected_oversize','fetch_failed_exhausted')
CHECK   octet_length(webhook_sha256) = 32
CHECK   webhook_size_bytes >= 0 AND webhook_size_bytes <= 65536     -- D7
CHECK   octet_length(raw_webhook) = webhook_size_bytes
CHECK   extensions.digest(raw_webhook,'sha256') = webhook_sha256    -- ver R6
FK      (company_id, inbox_id)         -> company_inboxes(company_id, id)
FK      (company_id, email_message_id) -> email_messages(company_id, id)
FK      (company_id, observed_blob_id) -> evidence_blobs(company_id, id)
```

**Ciclo de `state`** (no es una FSM mutable libre; cada transición es durable y acotada):
`received` *(fase 1, pre-fetch — estado de intake durable)* → exactamente uno de:
`captured` · `linked_existing` · `evidence_conflict` · `rejected_oversize`
*(terminales de fase 2)* · o `fetch_failed_exhausted` *(terminal tras agotar reintentos +
escalación, §4.7)*.

> **[Δ A3] Esto revisa A2.** A2 declaraba "sin estados FETCHING/CAPTURING" y "ACK=captured".
> El límite de 15 s (§1) hace inviable capturar el RAW de hasta 64 MiB antes del ACK, así que
> el estado `received` es intake durable pre-fetch y el RAW se captura en la fase 2 asíncrona
> durable (lo que ADR-047 ya anticipaba: "procesamiento asíncrono durable después"). Esta
> revisión requiere **ratificación del orquestador** (y auditoría Codex).

### 3.3 `inbound.email_messages`
```
id                   uuid        PK  DEFAULT gen_random_uuid()
company_id           uuid        NOT NULL
inbox_id             uuid        NOT NULL
provider             text        NOT NULL
provider_email_id    text        NOT NULL
internet_message_id  text        NULL            -- data.message_id, no único
raw_blob_id          uuid        NOT NULL        -- blob canónico del mensaje (inmutable)
provider_received_at timestamptz NULL
captured_at          timestamptz NOT NULL DEFAULT now()
created_at           timestamptz NOT NULL DEFAULT now()

PK      (id) · UNIQUE (company_id, id)
UNIQUE  (provider, provider_email_id, inbox_id)     -- idempotencia de MENSAJE
CHECK   provider = 'resend'
FK      (company_id, inbox_id)    -> company_inboxes(company_id, id)
FK      (company_id, raw_blob_id) -> evidence_blobs(company_id, id)
```

### 3.4 Outcomes, `observed_blob_id` e idempotencia

- **`observed_blob_id`** = el blob que vio ESTE evento; **`email_messages.raw_blob_id`** = el
  blob canónico del mensaje (nunca se sobrescribe).
- **Idempotencia de evento** `UNIQUE(provider, provider_event_id, inbox_id)`: el abanico
  multi-recipient genera una fila por `(evento, inbox)` con el mismo `svix-id`. Retry exacto →
  la fila ya existe → `ALREADY_FINALIZED` (resultado de runtime; sin fila nueva).
- **Idempotencia de mensaje** `UNIQUE(provider, provider_email_id, inbox_id)`:
  - email nuevo + RAW nuevo → crea blob + email + evento `state=captured`;
  - nuevo evento, email ya capturado, **mismo hash** → `state=linked_existing` (sin blob nuevo);
  - mismo `provider_email_id`, **hash distinto** → `evidence_conflict`: **nuevo** blob
    tenant-scoped con el RAW observado (hash/size exactos), `observed_blob_id`→ese blob,
    `email_message_id`→email canónico, **sin** tocar `raw_blob_id`, alerta fuerte.
- **Unknown/disabled recipient:** NO abre transacción tenant, NO inserta `provider_events`
  (no hay `company_id`/`inbox_id` que inventar); IGNORED + logging estructurado; ACK 2xx.

### 3.5 Invariantes de storage, inmutabilidad, RLS/grants, FKs tenant-safe

- **Invariante de storage** (tolerante a migración): los tres CHECK de §3.1 permiten el estado
  dual `bytes`+`object_locator` durante la migración futura y garantizan "nunca sin copia".
- **FKs tenant-safe compuestas** apoyadas en los UNIQUE `(company_id, id)` existentes de
  `inbound.company_inboxes` `[VERIFICADO: existe]` y los nuevos de las tres tablas.
- **RLS** ENABLE + FORCE; policies: `company_id = private.inbound_company_id()` (+ `inbox_id =
  private.inbound_inbox_id()` donde aplica).
- **Grants `inbound_backend`** **[Δ A3]**:

| Tabla | INSERT | SELECT | UPDATE | DELETE |
|---|---|---|---|---|
| `evidence_blobs` | ✔ | ✔ | ✖ (futuro: path migración, grant aparte) | ✖ |
| `email_messages` | ✔ | ✔ | ✖ | ✖ |
| `provider_events` | ✔ | ✔ | ✔ **solo** `state,attempts,next_attempt_at,last_error,email_message_id,observed_blob_id,captured_at` (col-level) | ✖ |

  > **[Δ A3]** La fase 2 necesita **UPDATE acotado por columnas** en `provider_events` para
  > avanzar el intake (`received`→terminal, backoff, enlaces). Las columnas de evidencia del
  > webhook (`raw_webhook`, `webhook_sha256`, identidades, `company_id`) permanecen inmutables
  > (sin grant de UPDATE sobre ellas). `evidence_blobs`/`email_messages` siguen append-only.
  > A2 proponía "sin UPDATE"; esta excepción mínima y columnar es necesaria y se declara
  > explícitamente. Sin triggers nuevos (no estorbar el migration path futuro de Object Storage).

## 4. C4-B3-A3 — diseño operativo

### 4.1 Captura en dos fases (resuelve R1)

```
FASE 1 — SÍNCRONA, PRE-ACK, presupuesto 15 s, diminuta y determinista
  recibir webhook → verificar Svix sobre RAW → parsear → routing por data.to (ADR-049)
  por cada recipient ACTIVE_RESOLVED:
      enter_inbound_context(recipient)
      INSERT provider_events(state='received', raw_webhook, identidades, attempts=0,
                             next_attempt_at=now())        -- ON CONFLICT → ALREADY_FINALIZED
  COMMIT  →  2xx                                           (unknown/disabled → IGNORED, 2xx)

FASE 2 — ASÍNCRONA, DURABLE, REINTENTABLE, IDEMPOTENTE (post-ACK)
  worker toma provider_events con state='received' y next_attempt_at<=now()
      GET Retrieve Received Email → raw.download_url (1 h)
      descarga en streaming con tope MAX (§4.3) y hash de una pasada
      BEGIN (inbound_transaction):
          idempotencia de mensaje (UNIQUE provider,provider_email_id,inbox_id)
          → captured | linked_existing | evidence_conflict   (§3.4)
          UPDATE provider_events.state = terminal, email_message_id, observed_blob_id
      COMMIT
  fallos → backoff (attempts++, next_attempt_at) hasta agotar → fetch_failed_exhausted + alerta
  oversize → rejected_oversize (terminal, §4.3)
```

Esto respeta el timeout de 15 s, la guía oficial de Svix ("encolar y responder pronto") y
ADR-047 ("captura durable síncrona antes del ACK" = el **evento verificado**; "procesamiento
asíncrono durable después" = fetch + persistencia del RAW).

**Garantía de no pérdida:** tras la fase 1 jamás perdemos *que* llegó un correo ni su
identidad (evento durable + `raw_webhook`). El cuerpo se recupera en fase 2 mientras Resend lo
retenga `[OBSERVADO ≥17 d]`; los reintentos deben completarse muy dentro de esa ventana (§4.7).

**Mecanismo de la fase 2 — depende de ADR-016 (⏳).** `provider_events` puede actuar como
**outbox/cola durable** (un worker sondea `state='received'`): sin infraestructura nueva, todo
en PG bajo RLS. Es la opción líder `[PROPUESTO]`, pero la **decisión formal es ADR-016** y
bloquea la implementación de la fase 2.

### 4.2 Presupuesto de 15 s (fase 1)
Verificar Svix (ms) + 1 roundtrip de resolución de tenant + N inserts pequeños + COMMIT. Con
`raw_webhook` acotado a ≤64 KiB (D7) y abanico típico pequeño, la fase 1 entra holgadamente en
15 s. La descarga del `.eml` (el cuello) queda **fuera** del camino del ACK.

### 4.3 Descarga RAW con streaming y límites efectivos (R2)
- Descarga del `download_url` **en streaming**, acumulando el hash SHA-256 **en una sola
  pasada**; contador de bytes.
- Si se supera `MAX_RAW_EMAIL_BYTES` (64 MiB) → **abortar** la descarga, **no** almacenar el
  oversize, persistir `state='rejected_oversize'` con el **límite aplicado**, **sin** afirmar
  sha256/size completos (no se calcularon). Preserva auditabilidad sin materializar el cuerpo.
- Nunca cargar el cuerpo entero en memoria para "medir después".

### 4.4 Concurrencia, memoria y backpressure (R3)
- La fase 2 es la que consume memoria (hasta 64 MiB por descarga en vuelo). **Tope de
  concurrencia** del worker `W` `[PROPUESTO: W pequeño, p.ej. 2–4]` → memoria máxima ≈
  `W × 64 MiB`, acotada y dimensionable contra la RAM del host (**depende de ADR-011**).
- Backpressure: si todos los slots están ocupados, las filas `received` simplemente esperan
  su turno (la cola es la tabla); no hay pérdida.
- La fase 1 no mantiene trabajo pesado → no compite por memoria ni por el pool de conexiones.

### 4.5 Idempotencia bajo carreras (R4)
- Fase 1: `INSERT ... ON CONFLICT (provider, provider_event_id, inbox_id) DO NOTHING`; si no
  insertó, es retry exacto → `ALREADY_FINALIZED`.
- Fase 2: un solo worker por fila vía **claim atómico** (`UPDATE ... WHERE state='received' AND
  next_attempt_at<=now() RETURNING ...`, o `SELECT ... FOR UPDATE SKIP LOCKED`), evita doble
  procesamiento.
- La creación de `email_messages` usa `ON CONFLICT (provider, provider_email_id, inbox_id)` →
  si otra entrega ganó la carrera, se relee el canónico y se decide `linked_existing` o
  `evidence_conflict` comparando el hash. Nivel de aislamiento y relectura explícitos en impl.

### 4.6 ACK multi-recipient y reintentos seguros (R4/D3)
- ACK HTTP = 2xx **sii** la fase 1 persistió el evento de **todos** los recipients activos (+
  IGNORED para unknown/disabled). Si falla la persistencia de alguno → non-2xx → Resend
  reintenta el evento completo; los ya insertados son idempotentes (`ALREADY_FINALIZED`).
- La fase 2 por recipient es independiente: un fallo de fetch de un tenant no afecta el ACK ni
  a los demás tenants.

### 4.7 Fallos persistentes de descarga y escalación (R5/D4)
- Clasificación de fallos de fetch: timeout, red, 429, 5xx, `download_url` caducada (re-pedir),
  404 inmediato tras webhook → todos **reintentables** (fail toward preserving evidence).
- Backoff con `attempts`/`next_attempt_at`; **presupuesto máximo de intentos/tiempo**
  `[PROPUESTO: p.ej. hasta ~7 días o N intentos, muy dentro de la retención ≥17 d]`.
- Al agotar → `state='fetch_failed_exhausted'` + **alerta** + visibilidad dead-letter; NUNCA un
  terminal "exitoso" falso. Posibilidad de **replay manual** de Resend como recurso.

### 4.8 Seguridad multitenant
- `inbound` backend-only (ADR-048/049): sin `service_role`, sin BYPASSRLS, sin JWT de
  navegador, sin membership ficticia. Contexto por `private.enter_inbound_context(recipient)`,
  revalidado por `private.inbound_company_id()/inbound_inbox_id()`.
- Autoridad de tenant = `data.to` exclusivamente (ADR-049); `received_for` solo traza.
- FKs compuestas (§3.5) hacen **estructuralmente imposible** referenciar recursos de otro
  tenant. Blobs **nunca** compartidos cross-tenant (un blob por tenant aunque los bytes
  coincidan). RLS ENABLE+FORCE en las tres tablas. El worker de fase 2 opera bajo contexto de
  tenant por fila.

### 4.9 Observabilidad sin PII (R8)
- Logging estructurado de outcomes (incl. IGNORED) con identificadores (svix-id, email_id,
  inbox_id, company_id, outcome, attempts) **sin** contenido del remitente ni secretos.
  `last_error` almacena diagnóstico de categoría, no cuerpos. `RESEND_WEBHOOK_SECRET` jamás se
  loguea.

### 4.10 Endpoint HTTP + mapeo de ACK (R7) — depende de ADR-011
- Nuevo router inbound montado en `app/main.py` (hoy solo se monta el router fiscal).
  `[VERIFICADO: no existe endpoint inbound]`.
- Mapeo: 2xx = fase 1 durable para todos; non-2xx = reintentar. Desplegar el endpoint productivo
  requiere la decisión de **hosting (ADR-011, ⏳)** y gestión del `RESEND_WEBHOOK_SECRET`
  productivo (rotado; nunca el del spike).

## 5. Evaluación de almacenamiento durable (punto 6 del orquestador)

**Pregunta:** ¿sigue PostgreSQL BYTEA siendo la mejor opción para la **captura inicial** dadas
las restricciones verificadas? **No se cambia la decisión sin autorización**; aquí van
alternativas y tradeoffs.

| Opción | Pros | Contras | Veredicto MVP |
|---|---|---|---|
| **A. PostgreSQL BYTEA** (decisión actual) | Atomicidad metadata+bytes+idempotencia en 1 tx; RLS nativa; sin infra/credenciales nuevas; integridad por `digest` CHECK; abstracción EvidenceBlob ya desacopla el futuro | Objetos de hasta 64 MiB inflan la DB (TOAST, backups, RAM de lectura); no es costo-eficiente a escala | **Mantener** `[PROPUESTO]` |
| **B. Object Storage ya (Supabase Storage/S3)** | Barato para bytes grandes; descarga la DB | Rompe atomicidad (2 sistemas → riesgo de huérfanos, requiere reconciliación); **introduce credenciales ahora** (ADR-050 lo prohíbe); RLS en Storage es superficie aparte; más piezas para el MVP | Diferir |
| **C. PostgreSQL Large Objects (`lo`)** | Streaming nativo; >1 GB | API incómoda; modelo de permisos aparte; mal encaje con RLS | Descartar |
| **D. Híbrido BYTEA≤umbral / Storage>umbral** | Equilibra costo y simplicidad | Complejidad prematura; dos caminos que mantener | Diferir (post-MVP) |

**Recomendación `[PROPUESTO]`:** **mantener BYTEA** para la captura inicial. A volumen de
MVP/pilotos, el costo/tamaño es inmaterial; BYTEA preserva la atomicidad y la aislación RLS que
son el objetivo; la abstracción EvidenceBlob hace la migración futura **no disruptiva**.
Nota: con la captura en dos fases (§4.1), los bytes pesados ya se escriben en la **fase 2**, lo
que hace la opción B más viable en el futuro **sin** cambiar la identidad del blob.

### Criterios medibles para migrar a Object Storage `[PROPUESTO — valores a ratificar]`
Disparar la migración (deuda ADR-050) cuando se cruce **cualquiera**:
1. bytes de evidencia en PG > **5–10 GB**, o > **20 %** del tamaño de la DB;
2. tasa de ingesta sostenida > **umbral** (p. ej. > 1–2 GB/semana de RAW);
3. p95 del tamaño de blob por encima de un bound que degrade lecturas/backups;
4. ventana de backup/restore > SLO operativo;
5. costo mensual de almacenamiento en PG > factor **k** del equivalente en Object Storage;
6. transición pilotos → comercial (N tenants de pago / M emails/día).

## 7. Tabla de riesgos residuales

| ID | Riesgo | Severidad | Mitigación propuesta | Estado |
|---|---|---|---|---|
| R1 | Captura síncrona de ≤64 MiB no cabe en 15 s | **Alta** | Captura en dos fases (§4.1); fase 1 diminuta | Mitigado por diseño; **pendiente ratificación** |
| R2 | Materializar el cuerpo para medir tamaño | Media | Streaming de una pasada + abort en MAX (§4.3) | Mitigado por diseño |
| R3 | Memoria por descargas concurrentes | Media | Tope `W` + backpressure vía cola (§4.4) | Mitigado; `W` **a dimensionar (ADR-011)** |
| R4 | Doble procesamiento / carreras | Media | `ON CONFLICT` + claim atómico/`SKIP LOCKED` (§4.5) | Mitigado por diseño |
| R5 | RAW irrecuperable → reintento infinito | Media | Backoff acotado + `fetch_failed_exhausted` + alerta (§4.7) | Mitigado; umbrales **a ratificar** |
| R6 | `extensions.digest` en CHECK (IMMUTABLE/search_path) | Media | Validar en diseño de migración; fallback = verificación en app + `octet_length` | **Abierto — verificar en migración** |
| R7 | Endpoint productivo sin hosting ni secreto gestionado | Media | Contrato de endpoint + ACK; **depende ADR-011** + secreto rotado | **Bloqueado por ADR-011** |
| R8 | Fuga de PII/secretos en logs | Media | Esquema de log por identificadores, sin cuerpos (§4.9) | Mitigado por diseño |
| R9 | Fase 2 sin mecanismo decidido | **Alta** | Outbox durable sobre `provider_events`; **depende ADR-016** | **Bloqueado por ADR-016** |
| R10 | Retención de Resend no contractual (`[OBSERVADO]`) | Media | Completar reintentos ≪ 17 d; replay manual como recurso | Aceptado con vigilancia |
| R11 | Dos fases revisan "sin estados parciales" y "sin UPDATE" de A2 | Media | Estado `received` durable + UPDATE columnar acotado (§3.2/§3.5) | **Pendiente ratificación** |
